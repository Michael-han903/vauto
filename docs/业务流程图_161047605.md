# 视觉自动化业务流程设计说明书

**场景**：Windows 平台赛车应用（UI 层自动化）
**共享挑战编号**：161047605
**文档性质**：业务流程设计 + 伪代码。**不含可执行代码**，业务实现留待对接方填充。

> **边界声明（重要）**
> 本文档只设计「屏幕看得到的东西 + 鼠标点得动的东西」：截图 → 模板匹配 → 移动/点击 → 窗口焦点守卫 → 急停。
> 不涉及内存读取、进程注入、封包修改、反检测对抗。若用于第三方软件，可能违反其用户许可协议（EULA），
> **存在账号被封禁的风险**，请先确认该应用的自动化条款。
> 文档中的所有阈值/超时均为**起始建议值**，必须在目标机器上实测标定（见第 5 节调参顺序）。

## 0. 假设与边界

| 编号 | 假设 | 若不成立的影响 |
|---|---|---|
| A1 | 挑战入口固定为 161047605，进入方式由人工完成或已由外部流程完成 | 需增加「进入挑战」子流程 |
| A2 | **「完成一轮挑战」由应用自身/人工完成**，本层只负责判定「一轮已结束」并点重试 | 若需本层驱动挑战内操作（如操控车辆），属于另一个复杂度量级的状态机，不在本文档范围 |
| A3 | 结算界面上的「重试」按钮在无结算面板时**不存在**（存在性即结束信号） | 若常驻，需改用「结算面板标题」做存在性判定 |
| A4 | 流程 B 的「条目」是可升级/可点亮对象的列表项，节点点击会消耗资源并使节点变为已激活 | 若点击不改变视觉状态，需增加资源计数器读数做推进依据 |
| A5 | 「资源不足」是**全局模态弹窗**，可能在 B 的任意一次点击之后出现，也可能在 A 中出现（同一资源池） | 见 1.4 异常表 |
| A6 | 单客户端、单实例、同一时刻只有一条流程在运行；B 由 A 的触发条件或多轮 A 之后进入 | 多实例需引入互斥与实例编号 |
| A7 | 所有识别基于固定分辨率/DPI 的模板匹配；窗口可缩放则启用多尺度 | 缩放会显著降低匹配稳定性 |

## 1. 文字版步骤描述

### 1.1 全局状态机（两条流程如何互切）

```
                 ┌──────────────────────────────┐
                 ↓                              │
   [IDLE] → [A: 挑战循环] ──触发B条件成立──→ [B: 条目批处理]
                                   │              │
                                   │    ┌─────────┘
                                   │    │ 出现「资源不足」弹窗
                                   └────┴──→ 退出B → 回到A
                                            │
                          资源耗尽/条目耗尽 → [END]
```

- **进入 A 的前置**：目标窗口存在且为前台；已在挑战入口界面（或由 A1 的人工步骤保证）。
- **A → B 的触发条件**（三者取一，由配置选择）：A 累计完成 N 轮后 / 重试按钮连续 K 次匹配失败 / 资源计数器读数高于阈值。
- **B → A 的退出条件**：出现「资源不足」弹窗，**或**条目列表已遍历完，**或**达到 B 的单次会话动作上限。
- 任一时刻只有一个流程处于 `RUNNING`，切换时必须先做「回到已知界面」的动作（关弹窗/按返回）。

### 1.2 流程 A：循环执行挑战

| 步 | 步骤名 | 描述 | 期望结果 | 超时/重试 |
|---|---|---|---|---|
| A0 | 焦点守卫 | 确认目标窗口为前台；非前台则暂停等待，不执行任何动作 | 前台 | 无限等（可被急停打断） |
| A1 | 等待结算 | 轮询截图，直到匹配到「重试」按钮 | 命中 → 一轮已结束 | 超时 T_settle（建议 90s）；超时进入 A1b |
| A1b | 超时自愈 | 按序尝试：① 再识别「挑战进行中 HUD」确认是否仍在进行 ② 处理遮挡弹窗 ③ 若都不成立则判定卡死，转人工/退出 | 恢复或退出 | 最多 T_max_retry 次（建议 3） |
| A2 | 定位并点击重试 | 命中坐标（相对客户区）→ 换算屏幕坐标 → 带抖动的仿真点击 | 触发下一轮 | 点击后进入 A3 校验 |
| A3 | 点击生效校验 | 等待「重试」按钮消失 **或** 「进行中 HUD」出现 | 已离开结算界面 | T_ack（建议 5s）；未生效则重试点击，最多 2 次 |
| A4 | 轮次记账 | `rounds_a += 1`，记录本轮耗时与匹配分数（日志） | — | — |
| A5 | 循环间隙 | 随机短暂休息（每 N 轮触发一次较长暂停） | 降低连续同频操作 | — |
| A6 | 回到 A1 | 继续下一轮 | — | — |

- **每轮必须重新截图**：结算界面的按钮位置会随轮次/动效漂移，禁止缓存坐标跨轮复用。
- **A 中的资源不足弹窗**：见 1.4，A 不吞掉该弹窗，直接按「资源耗尽」处理并结束任务（因为重试也消耗同一资源池，继续循环没有意义）。

### 1.3 流程 B：批量处理条目

| 步 | 步骤名 | 描述 | 期望结果 | 超时/重试 |
|---|---|---|---|---|
| B0 | 进入列表页 | 从 A 退出后，切换到条目列表页面（点击入口/返回上级），识别「列表页标题」确认到达 | 列表页已就绪 | T_page（建议 8s）；失败则返回重试 1 次 |
| B1 | 选择当前条目 | 若列表有多项：点击/滚动到第 `index_b` 项 | 该项被选中、出现子页面入口 | — |
| B2 | 打开子页面 | 点击该条目进入子页面，识别「子页面标题」确认 | 子页面已就绪 | T_page |
| B3 | 扫描节点 | 截图，识别所有**未激活**节点，得到候选列表（按扫描顺序排序） | 候选列表 | — |
| B4 | 逐个点击节点 | 对第一个候选：点击 → 等待状态变化 → 重新截图确认该节点已变为已激活 | 节点点亮 | 单节点最多 2 次点击；仍不变则跳过该节点 |
| B5 | 弹窗检查 | 每次点击之后、下一次点击之前，都必须检查「资源不足」弹窗 | 未出现 → 继续 B4；出现 → 转 B6 | — |
| B6 | 资源不足 → 退出 B | 记录现场（哪个条目/第几个节点）；关闭弹窗（点确定/关闭，如弹窗仅提供确定）；返回上级界面 | 回到 A 可运行的状态 | — |
| B7 | 条目推进 | 子页面无更多候选节点 → 返回列表 → `index_b += 1` → 回 B1 | 下一个条目 | 条目遍历完 → 结束任务 |
| B8 | 安全上限 | 单次 B 会话的节点点击总数不得超过 `max_node_clicks`（建议 200） | 防误判导致资源被无限消耗 | — |

- **B 的页面层级**：列表页 → 条目子页面 → （可能的二级子页面）。返回时**逐层返回**，每退一层都要用标题类元素确认到位，不能盲点返回键。
- **节点的识别策略（重要）**：优先用「未激活态外观」单一模板 + 位置去重（NMS）；当未激活/已激活两态外观接近时，**改用颜色/亮度判据**（对节点区域做 HSV 或灰度均值比较），比双模板更稳。双模板方案需两个模板都在同一分辨率下采集。
- **点击顺序**：按「从上到下、从左到右」的稳定顺序（避免随机顺序导致漏点/重点）。已点击并确认变化的节点不重复点。

### 1.4 异常与边界（两条流程共用）

| 异常 | 表现 | 处理策略 |
|---|---|---|
| 弹窗遮挡 | 公告/更新/网络异常/签到弹窗挡住主界面 | 每次关键识别**前**先做「通用关闭按钮」扫描（含右上角 X 与底部确定），关闭后再继续；同一弹窗连续 3 次关不掉 → 退出任务 |
| 加载慢 | 出现 loading 遮罩 | 识别到遮罩则等待，遮罩消失后再继续；计入该步超时 |
| 焦点丢失 | 前台窗口不是目标窗口 | 全部动作暂停，仅保留轮询；恢复前台后从**当前步**继续，不跳步 |
| 匹配分数抖动 | 分数在阈值附近反复横跳 | 采用「连续 2 帧命中」或分数滞回（进入 0.90 / 退出 0.80）消除抖动 |
| 资源不足（A 中） | 重试也消耗资源 | 立即结束任务并告警；不进入 B（避免连锁消耗） |
| 资源不足（B 中） | 任意节点点击后弹出 | 按 B6 退出 B、切回 A |
| 急停 | 人工按下 F1 | 立刻停止动作、释放所有按键/按钮、结束任务（最高优先级，任何步骤都要响应） |
| 窗口关闭/最小化 | 抓帧直接失败 | 结束任务并记录，不重试（重试无意义） |

| 变量 | 含义 | 建议值 |

### 3.2 运行期状态变量

| 变量 | 类型 | 初值 | 含义 |
|---|---|---|---|
| `flow` | 枚举 {A, B, END} | A | 当前所处流程 |

| `stop_flag` | 布尔 | 否 | 急停标志（最高优先级） |
| `paused_time` | 秒 | 0 | 因非前台累计暂停时长（日志/健康度） |
| `win_hwnd` | 句柄 | 启动时解析 | 目标窗口句柄 |
| `client_origin` | 坐标 | 启动时解析 | 客户区左上角的屏幕坐标（坐标换算基准） |

### 3.3 派生判定量（不落地为变量，但逻辑上必须存在）

- `should_enter_B` = `rounds_a ≥ ROUNDS_BEFORE_B` 或 `重试连续识别失败` 或 `资源计数 > 阈值`
- `should_exit_B` = `检测到资源不足弹窗` 或 `条目已遍历完` 或 `node_clicks_b ≥ MAX_NODE_CLICKS`
- `is_action_allowed` = `窗口在前台` 且 `未急停` 且 `未识别到加载遮罩`

## 4. 伪代码（仅逻辑，不可直接执行）

**约定**：`←` 表示取值/赋值；`「」` 表示原子动作；`◆` 表示必须做守卫检查；所有「等待」都指可被急停打断的等待。

### 4.1 公共原子动作

```
原子 等待可动作(超时):
    ◆ 若 已急停 → 抛出 中止
    ◆ 若 目标窗口不在前台 → 「暂停」直到回到前台(可被急停打断)；累计 paused_time
    ◆ 若 匹配(加载遮罩) 命中 且 持续 > 0.3s → 等待其消失(计入超时)
    返回 是否在超时内恢复可动作

原子 清遮挡弹窗(最大次数):
    重复 最大次数 次:
        ◆ 守卫
        若 匹配(资源不足弹窗) 命中 → 返回「资源不足」
        若 匹配(网络异常弹窗) 命中 → 返回「网络异常」
        若 匹配(通用关闭按钮) 命中 → 「点击其坐标」；继续
        否则 → 返回「干净」
    返回「关不掉」

原子 识别(模板, 阈值, 区域?, 取最佳?):
    ◆ 守卫
    「重新截取客户区一帧」
    命中列表 ← 「模板匹配(该帧, 模板, 阈值, 区域, 去重)」
    若 命中列表 非空 → 换算每个命中的「客户区坐标 → 屏幕坐标」后返回
    返回 空

原子 点击元素(元素/坐标):
    ◆ 守卫
    ①「先移到该点(曲线轨迹)」②「带像素抖动的按下-松开」③ 记录 last_click_pos
    等待 一个短随机间隔
```

### 4.2 流程 A：循环执行挑战

```
过程 流程A(进入条件已满足):
    重复 直到 应结束整个任务 或 应切换到B:

        // A1 等待一轮结束
        界末 ← 「等待结算界面出现」(轮询 匹配(challenge_retry_btn, TH_RETRY)
                                    或 匹配(challenge_result_panel, TH_TITLE)
                                    连续2帧命中才算成立)
        若 在 T_SETTLE 内出现:
            进入 A2
        否则:
            // A1b 超时自愈
            r ← 「清遮挡弹窗」(MAX_POPUP_CLOSE)
            若 r = 资源不足 → 结束任务并告警            // A 中也吃资源，不做B
            若 匹配(challenge_hud) 命中 → 本轮仍在进行，回到 A1 继续等待
            否则 consecutive_fail 累加
                 若 consecutive_fail ≥ 最大容忍 → 结束任务并记录现场(截图存档)
                 否则 回到 A1

        // A2 点击重试
        命中 ← 识别(challenge_retry_btn, TH_RETRY, 取最佳)
        若 命中 为空 → 回到 A1（可能已被动效/他人操作改变，重新判定）
        「点击元素(命中坐标)」

        // A3 校验点击生效
        生效 ← 「等待(challenge_retry_btn 消失 或 challenge_hud 出现)」在 T_ACK 内成立
        若 不成立:
            「点击元素(命中坐标)」再试一次
            若 第二次仍不成立 → consecutive_fail 累加；回到 A1

        // A4 记账
        rounds_a 累加；consecutive_fail 清零；写日志(轮次, 耗时, 分数)

        // A5 循环间隙
        「随机延时(0.6~1.6 × T_POLL)」
        若 rounds_a 是 REST_EVERY_N 的整数倍 且 随机命中概率 →
            「较长休息(REST_PAUSE)」

        // A6 触发判定
        若 should_enter_B 成立 → 返回「进入B」
```

### 4.3 流程 B：批量处理条目

```
过程 流程B:
    结果 ← 「进入条目列表页」
    若 结果 ≠ 到达 → 返回「无法进入B，回A」

    重复 当 index_b < 条目总数:
        // B1 选择条目
        「点击/滚动到第 index_b 项」；等待 T_POLL
        // B2 打开子页面
        若 「等待 subpage_title 出现」(T_PAGE) 不成立 → 跳到 B7(下一个条目)
        「随机延时」

        重复:
            // B3 扫描未激活节点
            区域 ← 识别(node_grid_anchor) 的坐标范围（作为搜索区域）
            候选 ← 识别(node_inactive, TH_NODE, 区域, 取全部) ← 去重后按 上→下/左→右 排序
            若 候选 为空 → 跳出内层循环（本条目处理完）

            // B4 点击第一个候选
            目标 ← 候选[0]
            「点击元素(目标)」；node_clicks_b 累加
            等待 T_POLL
            生效 ← 识别(node_active, 区域) 命中位置 ≈ 目标位置
            若 未生效:
                「点击元素(目标)」再试一次；仍不生效 → 标记该节点为「跳过」并从候选中剔除

            // B5 弹窗检查（每次点击后必查）
            r ← 「清遮挡弹窗」(MAX_POPUP_CLOSE)
            若 r = 资源不足:
                记录现场(条目 index_b, 第 node_clicks_b 次点击)
                「关闭弹窗 → 逐层返回上级界面（每层用标题确认）」
                返回「资源不足，回A」
            若 r = 网络异常:
                「逐层返回」；返回「网络异常，回A」
            若 r = 关不掉:
                返回「阻塞，人工介入」

            // B8 安全上限
            若 node_clicks_b ≥ MAX_NODE_CLICKS → 返回「达到动作上限，回A」

        // B7 条目推进
        「逐层返回列表页」（用 list_page_title 确认）
        index_b 累加
        若 识别(task_end_marker) 命中 → 结束整个任务
        「随机延时」；「按频率休息」

    返回「条目处理完，回A」
```

### 4.4 主调度

```
过程 主任务:
    ① 开启急停监听（默认 F1，按下即中止并释放所有按键）
    ② 解析窗口句柄；「开启客户区抓帧」；「加载全部模板」
    ③ 记录 client_origin（客户区左上角的屏幕坐标）
    ④ ◆ 等待目标窗口为前台

    循环 直到 急停 或 任务结束:
        ◆ 守卫
        若 flow = A:
            结果 ← 流程A()
            若 结果 = 进入B → flow ← B
            若 结果 = 结束 → 退出循环
        否则 若 flow = B:
            结果 ← 流程B()
            若 结果 以「回A」结尾 → flow ← A
            若 结果 = 结束 → 退出循环

    收尾:
        释放所有按下的按键/鼠标按钮
        保存末帧截图与日志（轮数, 条目数, 节点点击数, 暂停时长, 失败原因）
```

## 5. 实施顺序与调参建议

1. **先只做识别，不做点击**：用「dry-run」模式跑 10 分钟，把每类元素的命中分数与调试图存盘，确认：① 该命中的地方都命中 ② 不该命中的地方没命中（尤其 `challenge_retry_btn` 与 `popup_no_resource`）。
2. **标定阈值**：以实测分数的「最低值 − 0.03」作为阈值，不要凭感觉设 0.9。
3. **再开点击**，先跑 A 流程的 5 轮，核对：轮次记录是否与游戏内计数一致、重试是否只点一次。
4. **最后开 B 流程**，务必先把 `MAX_NODE_CLICKS` 设成 3~5 试跑，确认「资源不足弹窗 → 退出 B → 切回 A」这条路走得通，再放开上限。
5. **观察三个数字**：`consecutive_fail`（应长期为 0）、`paused_time`（高说明你总在切窗口）、`node_clicks_b`（异常增长说明节点状态判定失效，正在重复消耗资源）。
6. 全程保留 F1 急停与末帧截图；日志里必须能回答「上一轮为什么停」。
